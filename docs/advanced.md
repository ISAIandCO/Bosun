# Подробное руководство Bosun

[← Установка и интерфейс](../README.md)

Предел CPU задаётся через CPUFreq policy. Если текущая нижняя граница выше выбранного потолка, Bosun временно снижает её до потолка и сохраняет обе границы для отката. Доступность проверяется по аппаратному диапазону. При запуске/повторной синхронизации сохранённого игрового профиля его runtime-параметры имеют приоритет; обнаруженные изменения Steam сохраняются как новый baseline. Обычное глобальное применение и rollback сохраняют проверку внешних конфликтов. Запись `scaling_max_freq` не гарантирует соблюдение аппаратного потолка Boost/SMU: сравнивайте частоту под нагрузкой. Если оверлей превышает выбранное значение, нажмите **«Проверить CPU: лимиты и частоты (2 с)»** в блоке фактического состояния и сохраните его результат. Эта проверка показывает драйвер, активное назначение, реальные min/max policy и наблюдаемые частоты, включая источник показаний и возможный сброс лимита. `scaling_cur_freq` может отражать запрос драйвера; отсутствие превышения за короткий замер не доказывает соблюдение лимита во всей игре. [Почему интерфейсы различаются](https://docs.kernel.org/admin-guide/pm/cpufreq.html).

Настройки игры являются временными системными настройками и затрагивают остальные процессы устройства. Одновременно поддерживается одна игровая сессия. Если используете Decky-назначение, уберите launcher Bosun из launch options этой игры, чтобы два способа не пытались владеть одной сессией.

В профиле игры есть отдельная секция **«Параметры запуска Steam»**: прочитайте текущую строку, выберите параметры, посмотрите preview и примените. Доступны Mesa cache size, Proton auto/Fsync, DXVK queue latency, RADV wave32/NIR cache при поддержке установленным драйвером, I/O priority и affinity по физическим ядрам. Можно сохранить строку вручную. Steam запускает её обычным пользователем со следующего старта игры; она сохраняется между запусками, в отличие от временного системного overlay. Проценты ускорения для этих экспериментов не заявляются.

Оригинал сохраняется по **SteamID + AppID до записи**. Повторный preset строится от оригинала, не добавляет повторяющиеся префиксы. Внешнее изменение не затирается; «Оставить внешнюю строку» снимает владение. Для восстановления есть отдельная кнопка. Полный откат Decky сначала возвращает строки Steam, затем систему; для нескольких Steam-аккаунтов восстановите строки в каждом аккаунте. CLI rollback/uninstall сохранят приложение и объяснят блокер, пока остались управляемые строки. Прерванная запись видна как pending и может быть восстановлена. Native Steam API проверен контрактными тестами, но ещё требует проверки реальным клиентом на устройстве.

При временном скрытии бокового меню форма остаётся смонтированной штатным `alwaysRender` Decky: выбор в списке и черновик не теряются при возврате. Постоянного опроса для этого нет. Кнопки и поля размещены отдельными строками; действия используют всю ширину. При выходе из самого плагина несохранённый черновик не сохраняется.

События Steam относятся к внутреннему API клиента. При его изменении используйте кнопку **Синхронизировать текущую игру** и проверяйте состояние; аппаратная проверка отображения и событий на LCD/OLED ещё требуется.

## Профили и игры через CLI

CLI-launcher остаётся дополнительным способом. Системные назначения Decky работают по событиям Steam; процессные launch options редактируются отдельно.

```bash
bosun status
bosun apply recommended --dry-run
bosun apply recommended
bosun disable thp_defrag
bosun rollback --dry-run
```

При глобальном переключении старые настройки, которых нет в новом профиле, откатываются. Поэтому `bosun apply battery` заменяет рекомендуемый профиль; чтобы сохранить его системные настройки, создайте собственный профиль на его основе.

| Встроенный профиль | Содержимое | Назначение |
|---|---|---|
| `recommended` | Таблица выше | Системный стартовый набор |
| `cpu-game` | `powersave` governor + EPP `balance_performance` | Кандидат для CPU-sensitive игры; active amd-pstate сам выбирает частоту, `powersave` здесь не означает фиксацию низкой частоты |
| `gpu-game` | `powersave` + EPP `balance_power`, CPU ceiling 2800 MHz | Кандидат на перераспределение общего бюджета APU к GPU; может ухудшить CPU frametime |
| `battery` | `powersave` + EPP `balance_power`, Boost off | Только если целевой FPS/1% low сохраняются; Boost off может сильно замедлить игру |
| `memory-pressure` | Swappiness 150, zram readahead 0, MGLRU on | A/B при подтверждённых memory stalls; не меняет размер/компрессор zram |
| `memory-throughput` | MGLRU full, THP always, shmem within_size, proactive compaction0, page-lock unfairness8 | Эксперимент TLB/compaction при memory-heavy workload; риск background cost/фрагментации |
| `streaming` | Dirty writeback 200/400 MiB, vfs_cache_pressure50 | Отдельный A/B для asset streaming, не универсальные значения |
| `io-throughput` | NVMe/SD WBT0, SD BFQ idle0 при активном BFQ | Throughput против tail latency; сначала выбрать BFQ при необходимости |
| `background-overhead` | NMI/soft/hung-task checking off, VM stats15s, KSM stop | Меньше активной диагностики/сканирования; слабее диагностика зависаний |
| `stock` | Пустой профиль | Возврат сохранённых значений Bosun, не зашитых «заводских» настроек |

Сохранение и переключение:

```bash
# Системный профиль + свои параметры; установить явно, при желании после preview.
bosun profile-save my-game-system --base recommended --set epp=balance_power --set governor=powersave
bosun apply my-game-system --dry-run
bosun apply my-game-system

# Отдельный runtime-профиль для игрового launcher: пустая основа, только нужные параметры.
bosun profile-save my-game --base stock --set governor=powersave --set epp=balance_power --set cpu_max_mhz=2800 --set tdp_w=10
```

В параметрах запуска игры в Steam:

```text
/home/deck/.local/bin/bosun run my-game -- %command%
```

Launcher добавляет настройки игры к текущему глобальному профилю, запускает игру **обычным пользователем** и после выхода восстанавливает предыдущий профиль. Он работает в Desktop и Gaming Mode без запроса sudo при каждом запуске: установленный systemd path unit принимает запрос только на применение/возврат валидированного профиля. Команда игры не передаётся привилегированному помощнику. Помощник выполняется коротко по событию; постоянного процесса и polling-демона нет. Авторизация системного помощника выполняется при установке Bosun через sudo.
В игровой launcher нельзя включать загрузочные изменения, SMT, mount/memlock или менять CPU scheduler LAVD. Их применяют отдельно. При аварийном завершении launcher через SIGKILL сессия может остаться: достаточно явно применить нужный глобальный профиль: он заменит оставшуюся сессию без полного отката. Если хотите только завершить сессию и вернуть предыдущий профиль, её token виден в `bosun status`: выполните `bosun session-end --token TOKEN`. Поздний выход заменённого launcher сохраняет новый глобальный профиль. Одновременно допускается одна сессия системного power-профиля.

Профили — JSON без исполняемых команд в `~/.config/bosun/profiles`. `--set key=stock` убирает параметр из копии профиля. Список параметров: `bosun catalog`, подробности — [docs/tweaks.md](tweaks.md).

## Дополнительные настройки

Отдельно доступны CPU Boost, SMT, CPU ceiling, EPP/governor, APU TDP **4–15 W в пределах экспортируемых лимитов**, GPU policy `auto/low/high`, swappiness/THP, NVMe/microSD I/O scheduler, `amdgpu.moverate`, `scx_lavd` autopilot/balanced/powersave/performance. Также реализованы boot AMD P-state mode, GPU scheduler RR/FIFO, USB HID polling, memlock и отдельные VM/THP/writeback/NVMe/SD/zram controls. [Каталог](catalog.md) содержит допустимые значения и область каждого ключа; [разбор](global-analysis.md) — механизм, ожидаемый эффект и причины исключений.

Эти настройки требуют выбора по игре. Например:

```bash
bosun profile-save streaming --base recommended --set sd_scheduler=bfq
bosun profile-save migration-test --base recommended --set moverate=256
bosun profile-save lavd-test --base recommended --set lavd=autopilot
bosun apply lavd-test --dry-run
```

LAVD запускается отдельным принадлежащим Bosun unit только при наличии бинарника `scx_lavd`, sched_ext, BTF и отсутствии другого scheduler manager. Без поддержки sched_ext/BTF текущим ядром scheduler не включается, даже если пакет можно установить. Если `scx_lavd` отсутствует, при явном применении Bosun пытается установить `scx-scheds`/`scx` из настроенных SteamOS repositories. Сначала проверяется транзакция: изменение версий уже установленных зависимостей запрещено; переустановка того же пакета той же версии для восстановления отсутствующего бинарника допускается. Если совместимого провайдера нет, будет конкретная ошибка с предложением обновить SteamOS и повторить — чужие repositories и старые бинарники не подставляются. При ошибке attach транзакция откатывается; ядро также имеет механизм возврата к fair scheduler.

GPU frequency policy изменяется реально, но **ручная фиксация MHz не реализована**: на Deck `pp_od_clk_voltage` бывает пустым, поэтому скрытые старые limits нельзя надёжно сохранить для точного отката. Для fixed MHz используйте штатный профиль Steam, а в Bosun в этом случае не задавайте `gpu_mode`/TDP. Undervolt, разгон, повышение аппаратных пределов и отключение термозащит не выполняются.

Другие менеджеры питания (PowerTools, SimpleDeckyTDP, TLP, tuned и т. п.) обнаруживаются. Конкурирующие power-настройки пропускаются; остальные твики работают. Для power-профилей Bosun отключите управляющий сервис или удалите соответствующий Decky-плагин. Статическое наличие plugin.json считается конфликтом, чтобы не гадать, когда плагин начнёт управлять устройством.

## Приоритет игры, перезагрузка, сон, обновления SteamOS

При включённой автоматике сохранённые runtime-параметры игры перекрывают глобальные при каждом запуске. Плагин получает AppID из Steam lifetime notifications (с приоритетом над запаздывающим Router), применяет профиль через 750 мс и один раз проверяет/повторяет через ещё 1500 мс. Перезагрузка плагина при уже запущенной игре также выполняет начальное применение и один повтор через 1500 мс. Смена/выход/выгрузка отменяют устаревшие события; поздний exit предыдущей игры не отключает новую. CLI/legacy-сессия не блокирует назначение: она завершается, её токен аннулируется, затем применяется выбранная игра. После выхода возвращается предыдущий глобальный профиль; при отсутствии глобального значения — последнее сохранённое внешнее значение. В журнале приоритет отмечен `PRIORITY`. Строки запуска Steam и глобальные boot/service-файлы этим приоритетом не перезаписываются. Явное применение глобального профиля по-прежнему может завершить оставшуюся сессию в Desktop Mode.

Нет постоянно опрашивающего демона. Два systemd unit выполняют короткие проверки при загрузке и после сна, ещё одна пара path/service обслуживает запуск игровых профилей; `active (exited)` у sleep unit не означает работающий процесс.

* Runtime-настройки памяти/overhead, которыми Bosun действительно владеет, повторно проверяются. После сна возвращается только известное исходное значение, и только для управляемых непитающих настроек; неизвестное расхождение сохраняется как конфликт.
* Фоновый systemd resume не перезаписывает EPP, TDP, Boost, SMT и CPU/GPU power-настройки. Decky при включённой опции игры один раз применяет её сохранённые runtime-настройки с приоритетом над сбросами Steam, без постоянного опроса. После новой загрузки старая сессия истекает; запуск игры сам проверяет интерфейсы, снимает актуальный baseline и применяет назначение. Для CLI требуется запуск через `bosun run` или явный выбор профиля.
* При изменении `/etc/os-release`, ядра или версий Mesa/Gamescope фоновое восстановление глобального профиля останавливается до явного применения. Запуск сохранённого игрового назначения не требует этого действия: Bosun проверяет актуальные возможности и применяет доступные настройки. Для runtime-параметров сохраняется baseline новой загрузки/версии.
* Загрузочный override может сохраниться через SteamOS update; он остаётся активным, пока не отключён. Bosun не утверждает, что уже переданный ядру `mitigations=off` отменяется остановкой runtime replay. Проверяйте `cmdline` и фактические AMDGPU-параметры в статусе; изменение/откат требует reboot.

Bosun не заменяет ядро, Mesa, Gamescope или Proton. Недостающие утилиты устанавливаются отдельно через штатный pacman. Их замена здесь не обоснована измеренным преимуществом над вашим текущим стеком. [Разбор методов и источники](tweaks.md).

Параметр `lbpw` пересмотрен по исходникам: он относится к GFX9 и на Deck RDNA2 теперь пропускается. Подробнее — [аппаратные заметки](hardware-and-tweaks.md).

## Дополнительные эксперименты

Доступны `compaction_proactiveness`, `nvme_readahead_kb`, `sd_readahead_kb`, `zram_algorithm`, `zram_size_percent` и загрузочный `workqueue_power_efficient`. Это отдельные кандидаты для A/B, они не добавлены массово в recommended. Zram меняется только через собственный drop-in с применением после reboot: live swapoff не выполняется, другой владелец zram не заменяется автоматически. [Механизм, различия LCD/OLED и возможные регрессии](hardware-and-tweaks.md).

## Откат, конфликты, обновление и удаление

```bash
bosun rollback
# Если менялись boot-параметры — перезагрузиться.

python3 /home/.bosun/app/install.py --update
python3 /home/.bosun/app/install.py --uninstall
```

Для перехода со старой версии используйте свежий desktop-установщик по ссылке выше. Обновление также доступно через Decky, Desktop GUI и повторный запуск установщика. При обновлении плагина Decky перезапускается. При удалении Bosun его плагин удаляется, но Decky и установленные утилиты остаются: они могут использоваться другими программами. Оно не заменяет ваши профили и исходные значения твиков. Приложение, журнал и recovery-copy сохраняются в `/home/.bosun`; код и журнал защищены владельцем root. Это общий системный каталог на writable-разделе SteamOS, который не зависит от имени desktop-пользователя. Пользовательские CLI-профили лежат в `~/.config/bosun/profiles`; Decky backend получает root через флаг `root`. Запуск происходит от пользователя с повышением прав только для системных действий.

Перед записью журнал фиксирует исходное и целевое значения; после записи читается фактический результат. Повторное применение идемпотентно. Если запись не удалась, уже выполненные изменения транзакции возвращаются назад. После прерванной операции сначала выполняется recovery (`bosun recover`).

Если параметр после Bosun изменил Steam или другой инструмент, обычный откат **не затирает это изменение** и возвращает код 2. Для scalar-конфликта можно сохранить внешнее значение и снять владение: `bosun release epp`, затем повторить откат/применение. `release epp` и `release governor` освобождают связанную пару вместе, чтобы последующий возврат governor не сбросил сохранённый внешний EPP. `disable governor` возвращает оба значения; `disable epp` возвращает исходный EPP при сохранении выбранного governor. Это явное решение оставить внешнюю настройку, а не «возврат к stock». Для конфликтов прерванной транзакции верните спорный параметр в одно из двух значений из журнала (исходное или записанное Bosun), затем `bosun recover`. Загрузочные/service-файлы автоматически не освобождаются: сначала разрешите изменение файла, затем rollback. До полного разрешения конфликта удаление отказывается убирать программу.

Если версия до 0.3.2 сообщает `Generated GRUB has no Linux entries`, обновите Bosun: исправлено распознавание SteamOS-команды `steamenv_boot linux`. Такой отказ происходил до записи нового EFI-конфига. После обновления повторите применение.

GRUB изменяется через собственный `/etc/default/grub.d/zz-bosun.cfg`; действующий EFI target определяется по установленному `update-grub`. Конфиг генерируется во временный файл и проверяется `grub-script-check` перед атомарной записью. При неподдерживаемой схеме boot-твики пропускаются. Откат удаляет только собственный override и **перегенерирует текущий** GRUB; не подменяет конфигурацию старой копией поверх обновления системы. Recovery-copy перед записью находится в `/home/.bosun/state/grub-before.cfg`. Режим RO автоматически переводится в RW там, где нужна запись/установка пакетов, и возвращается в прежнее состояние в `finally`. Сохраняется recovery lease для восстановления режима после прерванной операции. Runtime-записи, получившие `EROFS`, повторяются в таком же контексте. Параметры, которые сам драйвер предоставляет только для чтения, не превращаются от этого в изменяемые.

## CPUFreq: асинхронные записи и прерванный откат

Linux записывает scaling_min/max_freq через freq_qos_update_request; notifier ставит policy update в workqueue. Немедленное чтение может вернуть старую границу. Bosun ожидает точного значения до 500 ms после записи, без постоянного опроса. Неизвестное/неустановившееся значение по-прежнему вызывает ошибку. Ступени scaling_available_frequencies учитываются до записи: потолок округляется вниз, при отсутствии подходящей ступени изменение пропускается.

Первичные источники: [CPUFreq QoS/worker, Linux 6.16](https://github.com/torvalds/linux/blob/v6.16/drivers/cpufreq/cpufreq.c), [frequency table resolution](https://github.com/torvalds/linux/blob/v6.16/drivers/cpufreq/freq_table.c), [документация CPUFreq](https://docs.kernel.org/admin-guide/pm/cpufreq.html). Это исправляет применение policy; измеренный аппаратный потолок Boost/SMU на Deck не подтверждён.

Если запускаемый игровой профиль содержит CPU cap, такой CPU-конфликт разрешается автоматически перед применением: журнал архивируется, CPU-границы принимаются как актуальный baseline, глобальный и игровой рецепты сохраняются. Остальной recovery выполняется обычным способом и не игнорирует чужие конфликты. Для ручного разрешения используйте кнопку «Разблокировать CPU, оставив текущие лимиты» или `bosun recover-cpu`. Это явный выбор оставить фактические CPU min/max: сохраняется полный архив `state/cpu-recovery-*.json`, снимается владение связанной парой CPU-границ в текущем и восстановительном снимке. Другие записи журнала не удаляются и возвращаются обычным recovery; неизвестный конфликт другого параметра блокирует его восстановление. Назначения игр сохраняются, последующее применение получает новые CPU baseline. Исходные CPU-значения остаются в архиве, автоматического возврата к ним после такого выбора нет.

В фактическом состоянии и CPU check показаны driver, min/max, источник частоты, доступные ступени и related_cpus. Для pending CPU-операции отдельно показаны before/intended/actual. Сравните их после успешного применения с оверлеем под игровой нагрузкой.
