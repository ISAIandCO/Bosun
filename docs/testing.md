# Проверки реализации и измерения на Steam Deck

## Фактически проверено

Физический Steam Deck в среде разработки отсутствует. Ни прирост FPS, ни снижение мощности, ни аппаратная совместимость LCD/OLED не измерены. DMI-модели и sysfs-интерфейсы проверены на изолированных fixtures. Это проверка логики программы, а не эмуляция драйверов GPU/SMU или доказательство загрузки реальной SteamOS.

```bash
python3 -m unittest discover -s tests -v
python3 -m py_compile bosun.py install.py bosun/*.py
```

Проверки охватывают preview без записи, реальные записи в изолированное дерево `/proc`/`sys`/`etc`/EFI, идемпотентность, точный откат исходных значений, отсутствие/неподдерживаемые параметры, LCD/OLED/неизвестную модель, swappiness с zram/disk swap, CPU/EPP/cap, TDP hardware bounds, GPU/SD policy, scheduler lifecycle, частичный сбой, journal recovery и его конфликт, загрузочный override, ошибку генератора, сохранение режима read-only, reboot/update baseline, resume без гонки со Steam, установку/обновление/удаление и game-session helper.

Boot generator/SMU/BPF в fixtures не исполняются. Shell-фрагмент GRUB исполняется в отдельном bash с тестовой cmdline; systemd unit-файлы проверяются отдельно. CI запускает те же тесты на Linux.

## Аппаратная приёмка

Выполнить отдельно на LCD и OLED; сохранить вывод `bosun status` до и после каждого шага.

1. В чистой Desktop-сессии установить desktop-ярлыком. Убедиться, что окно остаётся открытым при сетевой ошибке, пароль запрашивается штатным sudo, системные твики ещё не применены. Повторить установку как update.
2. `bosun apply recommended --dry-run`: нет изменения sysctl/sysfs/GRUB. Посмотреть SKIP и UNCHANGED; не считать их применёнными твиками.
3. Применить recommended, повторить. Проверить фактические значения. Перезагрузиться и проверить `/proc/cmdline`/CPU vulnerabilities, MGLRU, THP и zram page-cluster. Сверить прежний steamos-readonly status.
4. Проверить `systemctl status bosun-restore.service bosun-resume.service bosun-session.path`. У path unit нет постоянно работающего Bosun-процесса. `journalctl -u bosun-restore -u bosun-resume -u bosun-session` показывает ошибки/пропуски.
5. Создать runtime-only профиль игры с одним EPP/CPU cap, запустить через Steam wrapper в Gaming Mode. Перед игрой и после неё подтвердить apply/restore без запуска игры от root. Проверить нормальный выход, crash игры, SIGTERM wrapper; SIGKILL wrapper оставить для ручного recovery через token.
6. Suspend/resume в Desktop и Gaming Mode; проверить, что статические параметры вернулись только при известном reset, а Steam power changes не затираются. Повторно применить power-профиль явно.
7. Сменить Steam per-game TDP после применения Bosun TDP, запросить rollback. Ожидается конфликт с сохранением нового значения. `release tdp_w` должен оставить значение Steam; остальные параметры откатываются.
8. Если есть LAVD, проверить attach через `/sys/kernel/sched_ext/state`, ops, ошибку несовместимого бинарника, sleep и откат. Отдельно проверить, что активный scx_loader/PowerTools не перехватывается.
9. Полный rollback; reboot при загрузочных изменениях. Сравнить с сохранённым baseline. Не должно быть оставшегося override Bosun или изменённого режима read-only.
10. На следующем обычном обновлении SteamOS проверить pause автоматического replay, preview и новое явное применение. Не обновлять/откатывать систему только ради этого теста.
11. Uninstall должен сначала завершить rollback, а при внешнем конфликте сохранить приложение и объяснить причину. Проверить отсутствие активных Bosun units после удаления.

## Сопоставимый A/B-тест

Начать с отключённых других тюнеров, одинакового FPS cap/refresh, graphics/render scale, Proton, сцены/маршрута, версии игры и режима Desktop/Gaming. SSD/microSD, яркость, HDR, Wi-Fi, Bluetooth, звук, заряд и температура должны совпадать настолько, насколько возможно. Прошивки и версии ПО фиксируются, LCD и OLED не смешиваются.

* **A:** сохранённое состояние до Bosun (`rollback`, reboot если был boot-твик).
* **B:** один твик или recommended, reboot если нужен. Для поиска причины менять по одному параметру.
* Прогреть шейдеры/кеши и устройство одинаково; не очищать кеш только у одной стороны. Одинаково исключить loading/menus. Для streaming отдельно фиксировать cold/warm cache.
* Сделать минимум три повтора каждой конфигурации; порядок чередовать A/B/B/A/A/B. Один короткий run не отделяет эффект от шума/температуры.
* Для **сценария FPS/W** оставить одинаковый APU TDP и сравнить FPS, 1% low, frametime и реальную мощность батареи.
* Для **сценария автономности** оставить одинаковый target FPS и качество, подобрать профиль и проверить, что FPS/lows/pacing приемлемы, затем сравнить Wh на одном маршруте. Занижение TDP с ухудшением игры не считать успехом.

## Запись батареи

Без зарядного устройства и power delivery от dock. Запускайте в Konsole одновременно с игрой Desktop Mode; для Gaming Mode можно использовать SSH с другого ПК. Режим должен быть одинаковым в A и B.

```bash
cp /home/.bosun/app/docs/benchmark-metadata.json ~/bosun-test.json
# Заполнить фактические условия в JSON любым редактором.
mkdir -p ~/bosun-bench
bosun capture --seconds 300 --metadata ~/bosun-test.json --output ~/bosun-bench/A1.json
```

Измерение идёт **только 300 секунд** с частотой 1 Hz. Оно сохраняет модель, OS/kernel/Mesa/Gamescope, текущие interfaces/профиль, условия, memory PSI, zram stats и `power*_cap`. Если батарея перестала разряжаться, замер прерывается, неполный лог сохраняется без успешных итогов. Каждый запуск требует нового имени файла.

Используются `energy_now` (микроWh) и/или `power_now` (микроW), иначе `current_now × voltage_now`. Сохраняются **оба** результата, когда они доступны: расход Wh по счётчику и интеграл мощности. Средняя общесистемная мощность = `расход Wh × 3600 / длительность секунд`. Для слишком короткого участка gauge может не изменить energy_now; нулевой delta не выдаётся за нулевое потребление, используется интеграл, ограничение видно в результате. При слишком грубом gauge увеличьте длину маршрута и повторите тест.

`charge_now × текущее напряжение` не выдаётся за точный запас Wh: напряжение меняется в ходе разряда. APU cap и gpu_power — вспомогательные данные, **не мощность всего устройства**.

## Запись кадров MangoHud

Используйте уже установленный MangoHud. Для Proton/Vulkan в Steam launch options можно добавить:

```text
MANGOHUD=1 MANGOHUD_CONFIG=autostart_log=1,log_interval=0,log_duration=300,output_folder=/home/deck/bosun-bench %command%
```

Для desktop native OpenGL при необходимости используйте штатный `mangohud GAME`. Если игра требует wrapper Bosun, `%command%` в приведённой строке замените на `/home/deck/.local/bin/bosun run my-game -- %command%`. Не включайте два разных overlay/logger одновременно. Сверьте поддержку logging options с фактической версией MangoHud и проверьте, что файл создан.

`autostart_log` начинает запись с запуска: если в неё попали меню/загрузка, используйте штатный MangoHud toggle logging (обычно Shift+F2) в начале маршрута, убрав autostart, либо одинаково выделите нужный участок в обоих CSV. Запись батареи должна охватывать тот же участок. Не делите FPS одной сцены на мощность другой.

```bash
bosun analyze ~/bosun-bench/ИМЯ_MANGOHUD_LOG.csv
```

Анализатор ищет заголовок `frametime` после строк metadata, использует миллисекунды, выводит `1000 / mean(frametime)` и 1% low как `1000 / mean(самого медленного 1% кадров)`, median/P95/P99/P99.9 и spikes >50 ms. Нужны минимум 100 samples. **Периодический лог не даёт достоверный 1% low**: используйте raw/per-frame `log_interval=0`, проверьте характер файла и logger. Программа не притворяется, что способна установить per-frame режим по одному названию CSV.

## Интерпретация

В таблице результатов для каждого run: модель/версии, профиль и реальные применённые пункты, сцена/качество/cap/температура, mean FPS, 1% low, P99 ms, Wh, W всего устройства. Сравнивать медианы повторов и разброс, смотреть регрессии, а не только лучший run.

При сопоставимом тестовом участке можно посчитать `FPS / средние W` и `средние W / FPS` (J/frame). Для capped-сцены особенно полезны Wh и P99: одинаковый средний FPS может скрывать stutter. Автономность оценивать по usable battery Wh / общей мощности; не по номинальным TDP и не смешивая размер батарей LCD/OLED.

Если эффект меньше разброса, записать **«измеренного улучшения нет»**. Если FPS вырос, а расход непропорционально увеличился, профиль не подтвердил цель. Результаты этой версии пока ограничены проверкой реализации; заполненной аппаратной таблицы нет.
