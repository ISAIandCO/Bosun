# Проверки реализации и измерения на Steam Deck

## Фактически проверено

В версии 0.4.3: 159 Python-тестов и 34 frontend-теста проходят локально; TypeScript проверен, Decky bundle собирается. Физический Steam Deck в среде разработки отсутствует. Ни прирост FPS, ни снижение мощности, ни аппаратная совместимость LCD/OLED не измерены. DMI-модели и sysfs-интерфейсы проверены на изолированных fixtures. Это проверка логики программы, а не эмуляция драйверов GPU/SMU или доказательство загрузки реальной SteamOS.

```bash
python3 -m unittest discover -s tests -v
python3 -m py_compile bosun.py install.py bosun/*.py decky/main.py
npm --prefix decky ci --ignore-scripts
npm --prefix decky run check
npm --prefix decky run build
node --test decky/tests/*.test.cjs
python3 -m pip install PySide6-Essentials==6.9.3
QT_QPA_PLATFORM=offscreen python3 scripts/check-gui.py
```

Проверки охватывают preview без записи, реальные записи в изолированное дерево `/proc`/`sys`/`etc`/EFI, идемпотентность, точный откат исходных значений, отсутствие/неподдерживаемые параметры, LCD/OLED/неизвестную модель, swappiness с zram/disk swap, CPU/EPP/cap, TDP hardware bounds, GPU/SD policy, scheduler lifecycle, частичный сбой, journal recovery и его конфликт, загрузочный override, ошибку генератора, сохранение режима read-only, reboot/update baseline, resume без гонки со Steam, установку/обновление/удаление и game-session helper.

Регрессия прав Decky проверяется по установленным `plugin.json` и backend: root-процесс реально открывает журнал `0700`, сохраняет профиль и делает apply/rollback. При наличии UID/GID 1000 в namespace тест также запускает backend от обычного пользователя, воспроизводит отказ Unix permissions и проверяет понятную ошибку. В локальном контейнере отображён только UID 0; обе идентичности проверяются в Ubuntu CI.

В шести GRUB-регрессиях выполняется production-путь валидации/backup/записи; эмулируются только внешние grub-mkconfig/grub-script-check. Покрыты SteamOS steamenv_boot linux, linux/linuxefi, параметры cmdline, ошибка syntax checker и внешнее изменение EFI перед записью.

Девять React-регрессий монтируют настоящий компонент Content и проверяют цепочку изменение → предпросмотр/refresh → сохранение → вызов применения к текущей игре, глобальное применение, загрузку основы, смену AppID, ошибку сохранения, выключенную автоматику, явный сброс черновика и отображение SKIP. Подменяются native-компоненты Decky и RPC, а не логика состояния React. Дополнительный Python-тест выполняет реальные записи в изолированные CPU sysfs-fixtures при изменении уже активного назначения и проверяет точный возврат исходного значения после выхода.

Дополнительно шесть проверок выполняются и для исходников, и для поставляемого Decky bundle: host моделирует `(visible || activePlugin.alwaysRender) && activePlugin.content` из [Decky PluginView](https://github.com/SteamDeckHomebrew/decky-loader/blob/67196ad/frontend/src/components/PluginView.tsx). Проверяются callback выбора во время скрытия QAM, идентичность элемента списка до/после, сохранение системного и launch-черновиков, отсутствие повторной загрузки/опроса при hide/show, передача governor/TDP в применение, полноширинные действия в строках панели и readback отдельно от черновика (включая несовпадение и перевод единиц). На 0.3.3 четыре проверки hide/show и layout падали как на исходниках, так и на release bundle. Геометрия и native фокус Steam этими тестами не эмулируются.

CPU 0.3.5: одиннадцать Python-проверок используют строгую модель sysfs min ≤ max, восемь policies для обеих DMI-моделей, проверяют снижение и повышение потолка, точный откат, частичный отказ, восстановление прерванного изменения, конфликт связанной пары, baseline после reboot, повтор ранее пропущенного активного назначения и чтение частот/сброса без записи. Пять из первых шести регрессий падали на 0.3.4. Два frontend-сценария (source/bundle) проверяют кнопку краткого наблюдения, показ превышения рядом с фактическим состоянием и сохранение черновика без применения.

Boot generator/SMU/BPF в fixtures не исполняются. Shell-фрагмент GRUB исполняется в отдельном bash с тестовой cmdline; systemd unit-файлы проверяются отдельно. CI запускает те же тесты на Linux.

Интерфейс 0.4.0: одиннадцать Python-проверок покрывают runtime-фильтрацию всех глобальных ключей, CRUD своих профилей, отказ от неверных игровых назначений, удаление другого назначения без остановки текущей игры, JSON/CLI transport, авторизацию и подготовку зависимостей. Четыре frontend-проверки (source/bundle) проверяют игровые основы без boot/login-настроек, глобальный доступ к ним, сворачивание с сохранением компонента/черновика и текста launch options.

`scripts/check-gui.py` запускает настоящие Qt-виджеты с изолированным Control: preview без записи, apply/readback/rollback, изменение активного игрового назначения, сохранение рецепта, сохранение черновика при refresh, блокировку формы во время операции, отмену авторизации в настоящем QThread-пути. Проверяет отсутствие горизонтального переполнения пяти страниц и групп редактора при 1280×800 и 960×600; сохраняет снимки в `test-results/`. Снимки визуально проверены. Это offscreen-проверка Qt, не тест compositor/Polkit/KDE на Deck. Установка Qt на устройстве требует доступного совместимого пакета из его repositories; версия pip применяется только в разработке/CI.

Сессии 0.4.1: семь регрессий воспроизводят пропуск exit-события в той же загрузке и проверяют глобальные preview/apply, точный возврат CPU и памяти, идемпотентность, сохранение игрового назначения, позднее exit-событие, baseline следующего запуска, отказ записи с recovery, сохранение внешнего конфликта, отказ от неверных значений и прежнюю блокировку CLI-сессии (заменена в 0.4.2). CLI apply/disable используют тот же переход. Qt-сценарий открывает Desktop с оставшимся Decky-профилем и нажимает «Применить» recommended; проверяет снятие временного профиля и отсутствие возврата старых настроек при позднем exit.

Сессии 0.4.2: ограничение снято также для CLI/legacy, включая записи без owner. Пять новых сценариев падали на 0.4.1 с сообщением CLI launcher owns the active profile. Проверяются preview без записи, замена CLI-сессии, позднее и повторное завершение старого launcher при наличии новой сессии, атомарность commit профиля и аннулирования токена, сохранение токена при конфликте/ошибке, отказ от неизвестного/повторно использованного токена, ограниченный размер истории и восстановление после прерванного финального commit. Реальный subprocess внутри game_run меняет глобальный профиль и завершает работу с кодом 17: launcher сохраняет этот код, а его finally не откатывает новый профиль. Qt-сценарий воспроизводит и CLI-запись без owner, применяет recommended и проверяет поздний session-end.

CPUFreq 0.4.3: девять тестов проверяют отложенные QoS-записи min/max, восемь policies для обеих моделей, снижение/повышение/точный откат, дискретные ступени и отказ от неподдерживаемого потолка, строгий отказ при неизвестном readback, подробный recovery conflict, архивирование перед явным сохранением фактических CPU-границ, сохранение стороннего конфликта и отказ записи архива. Два теста отложенного readback/дискретных ступеней запускались против настоящих исходников 0.4.2 и падали. Кнопка recovery проверяется в исходном и поставляемом React bundle без сохранения/применения профиля, с сохранением черновика; Qt-сценарий нажимает её с реальным изолированным журналом и проверяет отсутствие записи CPU. Это не тест физического драйвера: источники задержек/конфликтов на устройстве нужно сверять по before/intended/actual, driver и доступным ступеням.

## Аппаратная приёмка

Выполнить отдельно на LCD и OLED; сохранить вывод `bosun status` до и после каждого шага.

1. В чистой Desktop-сессии установить desktop-ярлыком. Убедиться, что окно остаётся открытым при сетевой ошибке, пароль запрашивается штатным sudo, системные твики ещё не применены. Повторить установку как update.
2. Открыть ярлык Bosun: проверить боковую навигацию, группы/поиск, полную видимость кнопок и системное окно авторизации. Отменить авторизацию с черновиком — значения должны сохраниться. В Decky раскрыть/свернуть группы с геймпадом и проверить фокус. Убедиться, что игровые основы/список не содержат boot/zram/memlock/SMT/LAVD/mount; глобальный режим сохраняет доступ к ним.
3. `bosun apply recommended --dry-run`: нет изменения sysctl/sysfs/GRUB. Посмотреть SKIP и UNCHANGED; не считать их применёнными твиками.
4. Применить recommended, повторить. Проверить фактические значения. Перезагрузиться и проверить `/proc/cmdline`/CPU vulnerabilities, MGLRU, THP и zram page-cluster. Сверить прежний steamos-readonly status.
5. Проверить `systemctl status bosun-restore.service bosun-resume.service bosun-session.path`. У path unit нет постоянно работающего Bosun-процесса. `journalctl -u bosun-restore -u bosun-resume -u bosun-session` показывает ошибки/пропуски.
6. В Decky назначить профиль запущенной игре и другой игре по AppID: проверить автоприменение/возврат при старте, выходе и смене, сохранность назначений после обновления. Сравнить эффект с CLI-launcher, не включая оба способа одновременно. Проверить кнопку синхронизации, один resume replay и сохранение неизвестных внешних значений. Затем создать runtime-only профиль игры с одним EPP/CPU cap, запустить через Steam wrapper в Gaming Mode. Перед игрой и после неё подтвердить apply/restore без запуска игры от root. Проверить нормальный выход, crash игры, SIGTERM wrapper; SIGKILL wrapper оставить для ручного recovery через token.
7. Suspend/resume в Desktop и Gaming Mode; проверить, что статические параметры вернулись только при известном reset, а Steam power changes не затираются. Повторно применить power-профиль явно.
8. Сменить Steam per-game TDP после применения Bosun TDP, запросить rollback. Ожидается конфликт с сохранением нового значения. `release tdp_w` должен оставить значение Steam; остальные параметры откатываются.
9. Если есть LAVD, проверить attach через `/sys/kernel/sched_ext/state`, ops, ошибку несовместимого бинарника, sleep и откат. Отдельно проверить, что активный scx_loader/PowerTools не перехватывается.
10. Полный rollback; reboot при загрузочных изменениях. Сравнить с сохранённым baseline. Не должно быть оставшегося override Bosun или изменённого режима read-only.
11. На следующем обычном обновлении SteamOS проверить pause автоматического replay, preview и новое явное применение. Не обновлять/откатывать систему только ради этого теста.
12. Проверить автоматическую установку Decky при его отсутствии, сохранение чужих плагинов, загрузку официального бинарника/digest и появление интерфейса после возвращения в Gaming Mode. Проверить LAVD на устройстве без пакета: получение native provider, план без upgrades/downgrades и возврат RO при сетевой/пакетной ошибке.
13. Uninstall должен сначала завершить rollback, а при внешнем конфликте сохранить приложение и объяснить причину. Проверить отсутствие активных Bosun units после удаления.

Дополнительная приёмка Decky 0.3.3: на запущенной игре выбрать CPU cap 2800 MHz, выполнить предпросмотр и обновление состояния — значение должно остаться выбранным, но системное значение до применения не меняться. Нажать «Сохранить и применить к текущей игре» и сверить фактический `scaling_max_freq` доступных CPU policies. Сменить cap на 2400 MHz и повторить. После выхода сверить с исходным глобальным значением. Проверить EPP только при поддержке активным драйвером. При SKIP/CONFLICT читать причину рядом с кнопками; изменение TDP сверять с hwmon, не с ползунком Steam, которым Bosun не управляет. С выключенной автоматикой сохранение не должно менять sysfs. Отдельно проверить отмену черновика и ошибку сохранения без потери введённых значений.

Дополнительная приёмка Decky 0.3.4: проверить Gamepad/touch выбор governor, Boost, EPP, основы профиля и параметров запуска. Значение списка должно меняться без возврата к заголовку. После изменения CPU cap/TDP скрыть и вернуть QAM: черновик и положение фокуса должны сохраниться. Выполнить preview → сохранение/применение; сравнить выбранное с «ожидалось/прочитано» и sysfs. Проверить состояние после переключения в другую вкладку QAM, сна и повторного открытия; при внешнем изменении нажать обновление фактического состояния. Все кнопки, включая условные восстановление/конфликт и редактор Steam, должны помещаться по ширине панели. После выхода из самого плагина по кнопке назад несохранённый черновик закрывается.

Дополнительная приёмка CPU 0.3.5: на запущенной игре задать CPU cap 2400 MHz, сохранить/применить, сверить все policy min/max и оверлей под нагрузкой. Выполнить «Проверить CPU: лимиты и частоты (2 с)», сохранить результат, включая драйвер, kernel, Boost, активную игру, причины SKIP и источник частоты. Повторить с 2800 MHz. Непрерывное превышение при совпавшем policy cap требует отдельной проверки CPPC/Boost/SMU конкретной SteamOS; сам readback не является успехом. Если policy max не меняется или сбрасывается, сначала установить причину SKIP/внешнего писателя. При высоком исходном min проверить изменение обоих краёв и точный возврат после выхода/rollback, suspend и reboot. Не считать совпадение восьми regular-file fixtures проверкой физического драйвера.

Дополнительная приёмка 0.3:

* Проверить `/home` source/fstype/atime до и после apply/rollback; остальные flags сохраняются. Уже noatime — no-op. На отличающейся схеме mount — SKIP.
* Проверить zswap при zram-only и disk fallback; никакого swapoff/restart занятой zram. Zram compressor/size — после reboot.
* Проверить смену LAVD режима без зависания/старого unit; rollback возвращает старое состояние.
* Для Steam и non-Steam игры прочитать/изменить launch options через Decky, перезапустить игру, подтвердить env/affinity/I/O обычного пользователя. Убедиться, что HDR/graphics/cap не изменены. Проверить повтор preset, ручной editor, внешний конфликт, pending recovery, смену Steam-аккаунта и восстановление оригинала. Не считать mocked API доказательством совместимости реального Steam клиента.
* Writeback: проверить и bytes, и ratio после apply/rollback; memlock проверять после нового login/reboot, без перезапуска активной игровой сессии. Scheduler-specific queue tunables: выбрать scheduler, затем применить tuning; повторить на microSD и убедиться, что LCD eMMC исключён.

## Сопоставимый A/B-тест

Начать с отключённых других тюнеров, одинакового FPS cap/refresh, graphics/render scale, Proton, сцены/маршрута, версии игры и режима Desktop/Gaming. SSD/microSD, яркость, HDR, Wi-Fi, Bluetooth, звук, заряд и температура должны совпадать настолько, насколько возможно. Прошивки и версии ПО фиксируются, LCD и OLED не смешиваются.

* **A:** сохранённое состояние до Bosun (`rollback`, reboot если был boot-твик).
* **B:** один твик или recommended, reboot если нужен. Для поиска причины менять по одному параметру.
* Прогреть шейдеры/кеши и устройство одинаково; не очищать кеш только у одной стороны. Одинаково исключить loading/menus. Для streaming отдельно фиксировать cold/warm cache.
* Сделать минимум три повтора каждой конфигурации; порядок чередовать A/B/B/A/A/B. Один короткий run не отделяет эффект от шума/температуры.
* Для **сценария FPS/W** оставить одинаковый APU TDP и сравнить FPS, 1% low, frametime и реальную мощность батареи.
* Для **сценария автономности** оставить одинаковый target FPS и качество, подобрать профиль и проверить, что FPS/lows/pacing приемлемы, затем сравнить Wh на одном маршруте. Занижение TDP с ухудшением игры не считать успехом.

## Запись батареи

Без зарядного устройства и power delivery от dock. Запускайте в Konsole одновременно с игрой Desktop Mode; для Gaming Mode можно использовать SSH с другого ПК. Режим должен быть одинаковым в A и B.

```bash
cp /home/.bosun/app/docs/benchmark-metadata.json ~/bosun-test.json
# Заполнить фактические условия в JSON любым редактором.
mkdir -p ~/bosun-bench
bosun capture --seconds 300 --metadata ~/bosun-test.json --output ~/bosun-bench/A1.json
```

Измерение идёт **только 300 секунд** с частотой 1 Hz. Оно сохраняет модель, OS/kernel/Mesa/Gamescope, текущие interfaces/профиль, условия, memory PSI, zram stats и `power*_cap`. Если батарея перестала разряжаться, замер прерывается, неполный лог сохраняется без успешных итогов. Каждый запуск требует нового имени файла.

Используются `energy_now` (микроWh) и/или `power_now` (микроW), иначе `current_now × voltage_now`. Сохраняются **оба** результата, когда они доступны: расход Wh по счётчику и интеграл мощности. Средняя общесистемная мощность = `расход Wh × 3600 / длительность секунд`. Для слишком короткого участка gauge может не изменить energy_now; нулевой delta не выдаётся за нулевое потребление, используется интеграл, ограничение видно в результате. При слишком грубом gauge увеличьте длину маршрута и повторите тест.

`charge_now × текущее напряжение` не выдаётся за точный запас Wh: напряжение меняется в ходе разряда. APU cap и gpu_power — вспомогательные данные, **не мощность всего устройства**.

## Запись кадров MangoHud

Подготовьте native MangoHud кнопкой Decky или `bosun tools`: отсутствующий пакет установится автоматически, существующая версия сохранится. Для Flatpak runtime могут потребоваться соответствующие runtime extensions; Bosun не заменяет Flatpak graphics stack. Для Proton/Vulkan в Steam launch options можно добавить:

```text
MANGOHUD=1 MANGOHUD_CONFIG=autostart_log=1,log_interval=0,log_duration=300,output_folder=/home/deck/bosun-bench %command%
```

Для desktop native OpenGL при необходимости используйте штатный `mangohud GAME`. Если игра требует wrapper Bosun, `%command%` в приведённой строке замените на `/home/deck/.local/bin/bosun run my-game -- %command%`. Не включайте два разных overlay/logger одновременно. Сверьте поддержку logging options с фактической версией MangoHud и проверьте, что файл создан.

`autostart_log` начинает запись с запуска: если в неё попали меню/загрузка, используйте штатный MangoHud toggle logging (обычно Shift+F2) в начале маршрута, убрав autostart, либо одинаково выделите нужный участок в обоих CSV. Запись батареи должна охватывать тот же участок. Не делите FPS одной сцены на мощность другой.

```bash
bosun analyze ~/bosun-bench/ИМЯ_MANGOHUD_LOG.csv
```

Анализатор ищет заголовок `frametime` после строк metadata, использует миллисекунды, выводит `1000 / mean(frametime)` и 1% low как `1000 / mean(самого медленного 1% кадров)`, median/P95/P99/P99.9 и spikes >50 ms. Нужны минимум 100 samples. **Периодический лог не даёт достоверный 1% low**: используйте raw/per-frame `log_interval=0`, проверьте характер файла и logger. Программа не притворяется, что способна установить per-frame режим по одному названию CSV.

## Интерпретация

В таблице результатов для каждого run: модель/версии, профиль и реальные применённые пункты, сцена/качество/cap/температура, mean FPS, 1% low, P99 ms, Wh, W всего устройства. Сравнивать медианы повторов и разброс, смотреть регрессии, а не только лучший run.

При сопоставимом тестовом участке можно посчитать `FPS / средние W` и `средние W / FPS` (J/frame). Для capped-сцены особенно полезны Wh и P99: одинаковый средний FPS может скрывать stutter. Автономность оценивать по usable battery Wh / общей мощности; не по номинальным TDP и не смешивая размер батарей LCD/OLED.

Если эффект меньше разброса, записать **«измеренного улучшения нет»**. Если FPS вырос, а расход непропорционально увеличился, профиль не подтвердил цель. Результаты этой версии пока ограничены проверкой реализации; заполненной аппаратной таблицы нет.
